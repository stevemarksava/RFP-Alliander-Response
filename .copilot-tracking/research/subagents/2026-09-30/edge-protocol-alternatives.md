# Connect/Edge Layer Technical Alternatives — Protocols, Edge Compute, and Reference Architectures

Research scope: hardware-partner selection criteria for the Alliander schakellokalen (switchgear training room) "Connect (edge)" layer — instrumentation of MV/LV switchgear training equipment (switch position/state, current/voltage capture, RFID/NFC tagging, fault injection) feeding an on-site edge server that must run each training site fully offline and sync to Azure only when connectivity allows. Safety-critical interlocks and e-stop must remain physically independent of the digital layer.

Related workspace context: [4. Solution/Hardware Solution/alliander-schakellokalen-hardware-brd.md](4. Solution/Hardware Solution/alliander-schakellokalen-hardware-brd.md) already frames BR-003 as "industrial protocols (for example OPC-UA, Modbus, or MQTT) isolated from Alliander's corporate IT network" and requires the edge-to-cloud sync to be connectivity-optional, vendor-neutral, and safety-independent (SAFE-01/SAFE-02).

## 1. Industrial Communication Protocols

### OPC-UA

- Platform-independent, service-oriented architecture that unifies OPC Classic (DA/AE/HDA) into one extensible framework; runs from embedded micro-controllers to cloud infrastructure. ([OPC Foundation — Unified Architecture](https://opcfoundation.org/about/opc-technologies/opc-ua/))
- Real-time suitability: supports both client-server (request/response, subscriptions with report-by-exception) and Publish-Subscribe (PubSub) messaging models, so it covers both on-demand reads/writes and event-driven telemetry patterns needed for switch-state and sensor changes. ([OPC Foundation — Unified Architecture](https://opcfoundation.org/about/opc-technologies/opc-ua/))
- Security model: built-in session encryption, message signing (origin/integrity verification), sequenced packets (replay-attack protection), X.509-certificate-based mutual authentication between client and server applications, user-level authentication (credentials/certificate/token), access-rights-scoped "views," and audit logging — i.e., authentication, encryption, and auditing are native to the protocol rather than bolted on. ([OPC Foundation — Unified Architecture](https://opcfoundation.org/about/opc-technologies/opc-ua/))
- Independent security scrutiny exists and is actively maintained: multiple German BSI security analyses of the OPC UA specification and open-source stacks (2017, 2022), OPC Foundation practical security recommendation whitepapers, and a 2026 joint OPC Foundation/CISA paper on OT authentication barriers. ([OPC Foundation — Security](https://opcfoundation.org/security/))
- Azure integration: OPC UA is the reference "southbound" protocol for Microsoft's edge-connected IoT pattern. The official Microsoft **OPC Publisher** is an Azure IoT Edge module that is a fully compliant OPC UA PubSub telemetry publisher (JSON, JSON+Gzip, UADP binary), exposing OPC UA services via HTTP(s), an MQTT broker, or IoT Hub device methods — this is a direct, first-party path from switchgear OPC UA servers into Azure. ([Azure/Industrial-IoT — OPC Publisher](https://github.com/Azure/Industrial-IoT/blob/main/readme.md))
- In Microsoft's current Azure IoT architecture, OPC UA devices are explicitly the model "protocol-specific" (category 3) device class that connects through an edge runtime connector (Azure IoT Operations' OPC UA connector), confirming OPC UA is the expected/blessed protocol for this category of industrial asset. ([Microsoft Learn — Introduction to Azure IoT](https://learn.microsoft.com/en-us/azure/architecture/guide/iiot-guidance/iiot-architecture))
- Typical use: dominant in factory/process automation and is explicitly named alongside MQTT as the two standard southbound protocols for Azure's edge-connected industrial pattern.

### Modbus (TCP/RTU)

- Simple, openly published, royalty-free fieldbus protocol from 1979, still a de facto industrial standard; client/server (master/slave) request-response over serial (RTU/ASCII) or TCP/IP. ([Wikipedia — Modbus](https://en.wikipedia.org/wiki/Modbus))
- Real-time suitability: polling-based only — "there is no way for a field device to get data by the event handler mechanism... the client node must routinely poll each field device," which consumes bandwidth/time and is a weaker fit for asynchronous, low-latency switch-state change events than PubSub-style protocols. Address space limited to 247 devices per serial link. ([Wikipedia — Modbus, "Limitations"](https://en.wikipedia.org/wiki/Modbus))
- Security model: **none** — "Modbus protocol itself provides no security against unauthorized commands or interception of data." No native authentication or encryption; security must be entirely bolted on via network segmentation, VPN, or a gateway/wrapper. ([Wikipedia — Modbus, "Limitations"](https://en.wikipedia.org/wiki/Modbus))
- Azure integration: no first-party Azure IoT Edge Modbus module equivalent to OPC Publisher; Modbus access from Azure typically requires a third-party protocol-translation gateway (see HiveMQ Edge below) sitting in front of Azure IoT Edge/Operations.
- Typical use: extremely common for legacy PLCs, RTUs, and simple sensor/actuator I/O (coils, discrete inputs, holding registers) — a very plausible protocol for low-cost switch-position contacts or simple current/voltage transducers on training panels, but not a strong candidate as the *primary* site protocol given its lack of security and polling-only model.

### MQTT (and Sparkplug B)

- Lightweight publish/subscribe messaging protocol, purpose-built for constrained networks and event-driven delivery — a natural fit for asynchronous switch-state and telemetry "push" events rather than polling. Explicitly named as a standard edge/cloud messaging protocol in Azure's IoT architecture guidance. ([Microsoft Learn — Introduction to Azure IoT](https://learn.microsoft.com/en-us/azure/architecture/guide/iiot-guidance/iiot-architecture))
- **Sparkplug B** (Eclipse Tahu specification) layers OT-specific conventions on top of plain MQTT to solve exactly the gaps plain MQTT has for SCADA/DCS use: a well-defined topic namespace (device/edge-node context plus lifecycle "verbs"), an efficient binary payload (protobuf) suited to low-bandwidth/VSAT/radio/cellular links, and — critically — explicit **MQTT STATE management** using birth/death certificates built on MQTT's Last Will and Testament (LWT) feature, so subscribers can reliably detect when a device or edge node has gone offline/online (something plain MQTT does not standardize). ([Eclipse Tahu project page](https://projects.eclipse.org/projects/iot.tahu)) ([HiveMQ — MQTT Sparkplug essentials](https://www.hivemq.com/mqtt/mqtt-sparkplug-essentials))
- Security model: MQTT itself is transport-only (TLS for encryption, username/password or client-certificate/mutual-TLS for authentication at the broker); it has no protocol-native message signing or user-level access model equivalent to OPC UA. Security is a function of the broker and TLS/PKI configuration around it rather than the wire protocol.
- Azure integration: Azure IoT Operations ships an **edge-native MQTT broker** as its core data-plane component, with the OPC UA connector publishing device data onto MQTT topics at the edge, and downstream "data flows" bridging those topics to cloud endpoints (Event Grid/Event Hubs/Fabric OneLake). MQTT v3.1.1/v5 is the native protocol for "edge-connected (category 2)" devices in this architecture. ([Microsoft Learn — What is Azure IoT Operations?](https://learn.microsoft.com/en-us/azure/iot-operations/overview-iot-operations))
- Vendor-neutral tooling exists to convert Modbus/OPC UA/Siemens/EtherNet-IP/BACnet into MQTT at the edge (e.g., HiveMQ Edge protocol adapters), explicitly including offline buffering so messages are queued on disk and published once connectivity returns — directly supporting the offline-first requirement. ([HiveMQ Edge](https://www.hivemq.com/products/hivemq-edge/))
- Typical use: Sparkplug B/MQTT is the emerging standard for IIoT "Unified Namespace" architectures bridging OT and IT, and is explicitly called out by the user's own framing as a strong candidate for OT/IT integration.

### IEC 61850 (additional strong candidate for this grid-training context)

- International standard for communication protocols between intelligent electronic devices (IEDs) at electrical substations, maintained by IEC Technical Committee 57 specifically for electric power automation. ([Wikipedia — IEC 61850](https://en.wikipedia.org/wiki/IEC_61850))
- Defines **GOOSE** (Generic Object Oriented Substation Event) for fast, event-driven binary/state change messaging (e.g., breaker/switch position changes) directly over Ethernet multicast with sub-millisecond-class latency — purpose-built for exactly the "switch position/state sensing" real-time requirement in this BRD — plus Sampled Values (SV/SMV) for continuous current/voltage waveform capture, and MMS for higher-level client-server data access. ([Wikipedia — IEC 61850](https://en.wikipedia.org/wiki/IEC_61850))
- Security model: base IEC 61850 communication (GOOSE/SV) was not originally designed with authentication/encryption; security is layered on via the companion standard **IEC 62351** (referenced as a base standard of IEC 61850's ecosystem). ([Wikipedia — IEC 61850](https://en.wikipedia.org/wiki/IEC_61850))
- Azure integration: no first-party Azure IoT Edge/Operations connector for IEC 61850 GOOSE/SV exists in Microsoft's current documented southbound connector set (OPC UA, ONVIF, HTTP/REST, custom connectors via Akri) — integration would require a gateway device (RTU/substation gateway or PC) that terminates IEC 61850 and re-publishes via OPC UA or MQTT.
- Typical use: IEC 61850 is the dominant real-world standard specifically for substation/switchgear automation and protection, which makes it strong domain-authentic terminology for an MV/LV switchgear *training* simulator (the panels being trained on, in the real world, would very likely speak IEC 61850 GOOSE for breaker status) — but for a *training rig*'s sensor instrumentation layer, its lack of a native Azure connector is a material integration cost versus OPC UA/MQTT.

### Protocol comparison summary

| Protocol | Real-time telemetry fit | Azure IoT Edge/Operations integration | Offline operation | Native security |
| --- | --- | --- | --- | --- |
| OPC UA | Strong (client-server + PubSub, subscriptions/report-by-exception) | First-party (OPC Publisher module; Azure IoT Operations OPC UA connector) | Works locally; only the edge-to-cloud hop needs connectivity | Strong — X.509 mutual auth, encryption, signing, auditing |
| Modbus TCP/RTU | Weak-moderate (polling only, no event push) | None first-party; needs a gateway | Fully local by design | None — must be bolted on |
| MQTT (+ Sparkplug B) | Strong (pub/sub, event-driven; Sparkplug adds birth/death state awareness) | First-party (Azure IoT Operations edge-native MQTT broker) | Strong — broker/bridge products offer disk-backed offline buffering | Transport-only (TLS + broker auth); no protocol-native signing/auditing |
| IEC 61850 (GOOSE/SV) | Very strong for switch/breaker state and waveform capture specifically | None first-party — needs a translation gateway | Fully local by design | Only via companion IEC 62351 |

### Recommended protocol approach

**Recommend a layered combination: OPC UA as the primary southbound/edge protocol, with MQTT (Sparkplug B convention) as the edge-to-cloud and event-distribution layer, and Modbus reserved only for simple legacy sensor I/O behind a gateway.** Rationale: OPC UA gives the instrumentation layer native, certificate-based security and a rich information model appropriate for switch-state, current/voltage, and RFID/NFC tag data, and it has a first-party, Microsoft-maintained bridge (OPC Publisher / Azure IoT Operations OPC UA connector) into Azure. MQTT/Sparkplug B is the right choice for the edge's internal event bus and for the edge-to-cloud sync hop because it is what Azure IoT Operations' edge-native broker speaks natively, it is lightweight enough for intermittent/low-bandwidth links, and Sparkplug B's birth/death "state" convention directly solves the "was this training panel connected during this exercise" problem that a fully offline, session-based training system needs. Modbus should not be excluded outright — much low-cost switch-contact and current-clamp hardware is Modbus-native — but it should sit behind a protocol-translation adapter (e.g., HiveMQ Edge) rather than being exposed as a site-wide protocol, given its complete absence of authentication/encryption. IEC 61850 is worth flagging to the hardware partner as a "nice to have" companion spec for authenticity to real substation equipment, but should not be mandated as the core telemetry protocol given the lack of a first-party Azure connector — this would add integration cost without a corresponding security or reliability benefit for a *training* rig (as opposed to a live substation).

## 2. Edge Compute Platform Options

### Azure IoT Edge (classic)

- Device-focused container runtime (Docker-compatible modules) that brings cloud logic and analytics to the edge for "offline decision-making"; runs natively on Linux and on Windows via IoT Edge for Linux on Windows (EFLOW); supports Java, .NET, Node.js, C, Python. ([Microsoft Learn — What is Azure IoT Edge?](https://learn.microsoft.com/en-us/azure/iot-edge/about-iot-edge?view=iotedge-2.0))
- Offline capability is explicit and strong: after a one-time initial sync with IoT Hub, "the IoT Edge device, its deployed modules, and any downstream devices can keep operating **indefinitely**" while disconnected — there is no documented maximum offline duration for classic IoT Edge (only message time-to-live and local disk space bound how much telemetry history is retained). On reconnect, locally stored messages are delivered in original order and device/module state is reconciled. ([Microsoft Learn — Operate Azure IoT Edge devices offline](https://learn.microsoft.com/en-us/azure/iot-edge/offline-capabilities?view=iotedge-1.5))
- Local scenario-engine hosting: modules are plain containers, so a custom training scenario-engine, fault-injection logic, and instructor dashboard can run as first-class IoT Edge modules alongside protocol modules (e.g., OPC Publisher), with module-to-module communication continuing to work fully offline via the local edgeHub.
- Resilience/UPS pattern: IoT Edge is device/OS-level software, so UPS and resilience are handled by the underlying industrial PC/gateway hardware (matching BR-004's UPS requirement) rather than by IoT Edge itself; IoT Edge's own local storage and TTL settings determine how much buffered telemetry survives a power event.
- Sync-back-to-cloud: designed around IoT Hub's device/module twin model plus store-and-forward — this is a mature, well-documented pattern purpose-built for exactly "sync to cloud only when connectivity becomes available."

### Azure IoT Operations (Microsoft's current recommended edge-connected platform)

- Microsoft's newer, actively promoted platform for edge-connected/OT scenarios: a Kubernetes-native (Azure Arc-enabled Kubernetes) unified data plane including an edge-native MQTT broker, Akri connectors (OPC UA, HTTP/REST, custom), and data-flow transformation/routing to cloud endpoints (Event Grid, Event Hubs/Kafka, ADLS, Fabric OneLake, Azure Data Explorer). It is explicitly "Microsoft's recommended platform for new edge-connected solutions." ([Microsoft Learn — What is Azure IoT Operations?](https://learn.microsoft.com/en-us/azure/iot-operations/overview-iot-operations)) ([Microsoft Learn — Introduction to Azure IoT](https://learn.microsoft.com/en-us/azure/architecture/guide/iiot-guidance/iiot-architecture))
- **Material constraint versus the BRD's "fully offline" requirement:** Azure IoT Operations documentation states it "can operate offline for a maximum of **72 hours**. Degradation might occur during this period. However, the service resumes full functionality when it reconnects." ([Microsoft Learn — What is Azure IoT Operations?](https://learn.microsoft.com/en-us/azure/iot-operations/overview-iot-operations)) This is a documented ceiling, not an indefinite guarantee, and is a direct risk against a training site that may have no internet breakout for long, unscheduled periods.
- Management plane: managed via Azure Arc, giving cloud-based fleet management, GitOps-based configuration (Argo CD/Flux v2), Azure Monitor, Defender for Containers, and Azure Policy across distributed Kubernetes clusters running anywhere. ([Microsoft Learn — Overview of Azure Arc-enabled Kubernetes](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/overview))
- Local scenario-engine hosting: strong, since it is Kubernetes-native — a custom scenario engine/digital twin/scoring service can be deployed as a normal Kubernetes workload alongside the MQTT broker and connectors.
- Operational complexity: requires standing up and operating an on-site Kubernetes cluster (or AKS Edge Essentials on Windows/Ubuntu for the local deployment quickstart), which is materially heavier infrastructure than a single IoT Edge device/VM for a small training-room deployment. ([Microsoft Learn — What is Azure IoT Operations?](https://learn.microsoft.com/en-us/azure/iot-operations/overview-iot-operations))

### Azure Local (formerly Azure Stack HCI) / Azure Arc-enabled edge infrastructure

- Microsoft's distributed on-premises infrastructure product: extends Azure capabilities (portal, CLI, ARM templates, Azure Policy, Defender for Cloud, Azure Monitor) to customer-owned hardware via Azure Arc as the unifying control plane; explicitly supports deployments "connected or disconnected from the cloud." ([Microsoft Learn — What Is Azure Local?](https://learn.microsoft.com/en-us/azure-stack/hci/overview))
- Positioned for "mission critical business continuity required for systems that must continue to run through network outages... production line operations in factories," and "control systems and near real-time operations that have extreme latency requirements... manufacturing execution systems, industrial quality assurance" — a strong conceptual match to a training site that must never depend on connectivity. ([Microsoft Learn — What Is Azure Local?](https://learn.microsoft.com/en-us/azure-stack/hci/overview))
- This is effectively the **infrastructure/hypervisor layer** underneath edge workloads (it is validated hyperconverged hardware + Arc, not a data-plane/protocol runtime by itself); Azure IoT Edge or Azure IoT Operations would still run as the workload on top of Azure Local. It is priced per physical core and requires a prescriptive, partner-validated Bill of Materials from the hardware catalog, which cuts against a "no fixed SKUs" vendor-neutral posture.
- No direct documented "disconnected operations" duration limit was found for Azure Local itself in this research pass (the specific disconnected-operations guidance page returned a 404); this should be validated directly with Microsoft/partner documentation before committing to it as the infrastructure layer, rather than assumed.

### Vendor-neutral industrial edge gateway (e.g., HiveMQ Edge, Kepware/PTC, Ignition Edge) fronting Azure IoT Edge

- Software-based edge MQTT gateway/protocol converter pattern: translates Modbus, OPC UA, Siemens, EtherNet/IP, BACnet, and other OT protocols into standardized MQTT, runs on standard hardware or Kubernetes, and explicitly provides an **offline buffer** — "messages are stored on disk and published once online" — directly matching the "run fully offline, sync when available" requirement at the protocol-adapter layer. ([HiveMQ Edge](https://www.hivemq.com/products/hivemq-edge/))
- This class of product is a *complement* to, not a substitute for, Azure IoT Edge/Operations: it normalizes heterogeneous switchgear-instrumentation protocols into one bus (MQTT/Sparkplug) at the very edge, which Azure IoT Edge or Azure IoT Operations then consumes and forwards to Azure — this is exactly the "vendor-neutral, no fixed SKUs" posture the BRD asks for, because the hardware partner's sensor choices stay decoupled from the Azure-facing layer.

### Edge compute platform comparison summary

| Option | Offline-first capability | Local scenario-engine hosting | UPS/resilience pattern | Azure reconnect/sync model |
| --- | --- | --- | --- | --- |
| Azure IoT Edge (classic) | Indefinite offline after initial sync (documented, no max duration) | Yes — standard containers/modules | Handled by underlying industrial PC + UPS; IoT Edge buffers per TTL/disk | Store-and-forward to IoT Hub; ordered delivery, twin reconciliation on reconnect |
| Azure IoT Operations | Documented **72-hour** offline ceiling with degradation | Yes — Kubernetes-native workloads | Handled by underlying Arc-enabled cluster infrastructure | Data flows to Event Grid/Event Hubs/Fabric on reconnect; Arc-managed |
| Azure Local (Arc-enabled edge infra) | Supports connected/disconnected deployments (infrastructure layer); no documented max-offline duration found in this pass | Indirect — hosts IoT Edge/Operations or VMs as workloads | Part of validated HCI hardware BOM; per-core licensing | Arc control-plane reconnect; workload-dependent sync |
| Vendor-neutral OT gateway (e.g., HiveMQ Edge) + Azure IoT Edge | Strong — disk-backed offline buffering at the protocol-adapter layer | No (protocol translation only; scenario engine runs elsewhere, e.g., in IoT Edge modules) | Independent of Azure; runs on any standard/industrial hardware | Bridges to Azure IoT Edge/Hub or cloud MQTT broker once online |

### Recommended edge compute approach

**Recommend Azure IoT Edge (classic) as the primary on-site runtime, fronted by a vendor-neutral protocol-adapter layer (e.g., HiveMQ Edge–class gateway or equivalent) for Modbus/legacy sensor translation, rather than Azure IoT Operations or Azure Local as the initial platform.** Rationale: classic Azure IoT Edge is the only one of the four options with a documented, indefinite offline-operation guarantee (extended-duration disconnection is its whole design point), whereas Azure IoT Operations — Microsoft's newer, more strategically promoted platform — carries a documented 72-hour offline ceiling with degradation, which is a direct conflict with a training site that may be disconnected for unpredictable and potentially longer periods. Azure IoT Edge also runs as a single device/VM rather than requiring a full on-site Kubernetes cluster, which better matches a "vendor-neutral, no fixed SKUs" training-room deployment than Azure Local's prescriptive, partner-validated hardware catalog. This recommendation should be treated as provisional pending direct confirmation with Microsoft/the hardware partner of (a) Azure IoT Edge's current long-term support roadmap relative to Azure IoT Operations, since Microsoft Learn material increasingly frames IoT Operations as the forward-looking recommendation for edge-connected/OT scenarios, and (b) whether a future need for edge-hosted AI/agentic scoring at Kubernetes scale would eventually justify migrating to Azure IoT Operations once its offline-duration guarantees mature or the operational requirement for multi-day disconnection is relaxed.

## 3. Reference Architectures and Microsoft Guidance

- **Introduction to Azure IoT** (Azure Architecture Center / Microsoft Learn) is the canonical current source defining the "edge-connected pattern" versus "cloud-connected pattern," the category 1/2/3 device taxonomy, and the recommendation to use Azure IoT Operations plus Azure Device Registry for OT/industrial scenarios with OPC UA/MQTT southbound connectivity — directly describes this project's shape (on-site edge processing devices that speak an industrial protocol, forwarding to the cloud only after local processing). ([Microsoft Learn — Introduction to Azure IoT](https://learn.microsoft.com/en-us/azure/architecture/guide/iiot-guidance/iiot-architecture))
- **Operate Azure IoT Edge devices offline** is the authoritative Microsoft Learn reference for the classic-IoT-Edge offline-first pattern: parent/child (transparent gateway) topology, store-and-forward semantics, time-to-live and host-storage tuning, and reconnect/resync behavior — this is the specific "offline-first edge to cloud" guidance most directly applicable to the BRD's synchronization requirement. ([Microsoft Learn — Operate Azure IoT Edge devices offline](https://learn.microsoft.com/en-us/azure/iot-edge/offline-capabilities?view=iotedge-1.5))
- **What Is Azure IoT Operations?** documents the modern edge-connected architecture (Arc-enabled Kubernetes, edge-native MQTT broker, Akri connectors, data flows to Fabric) and is the source of the 72-hour offline ceiling that is the key risk flag against using it as the sole edge platform for this scenario. ([Microsoft Learn — What is Azure IoT Operations?](https://learn.microsoft.com/en-us/azure/iot-operations/overview-iot-operations))
- **Microsoft OPC Publisher / Azure Industrial IoT** (GitHub, Azure org) is the first-party reference implementation bridging OPC UA industrial assets into Azure IoT Edge/Hub, and is the concrete artifact a hardware partner would integrate against for switch-state/sensor OPC UA servers. ([Azure/Industrial-IoT](https://github.com/Azure/Industrial-IoT/blob/main/readme.md))
- **What is Azure Digital Twins?** describes the DTDL-modeled twin-graph pattern (models → twins → relationships), IoT Hub-driven property updates, and event-routing to downstream analytics — the relevant cloud-side pattern for the "live digital twin and AI/agentic scoring layer" once devices are digitally connected, consuming the store-and-forward telemetry that arrives from the edge after reconnect. ([Microsoft Learn — What is Azure Digital Twins?](https://learn.microsoft.com/en-us/azure/digital-twins/overview))
- **What Is Azure Local?** frames the disconnected-capable on-premises infrastructure story (Arc as control plane, connected-or-disconnected deployment, per-core pricing, partner hardware catalog); no dedicated "disconnected operations" page could be retrieved in this pass (404) and that specific operational-limits documentation should be pulled directly during vendor due diligence rather than assumed from the overview page alone. ([Microsoft Learn — What Is Azure Local?](https://learn.microsoft.com/en-us/azure-stack/hci/overview))
- No published Microsoft Learn or Azure Architecture Center reference architecture specifically titled for "industrial training simulator" or "grid/switchgear training" was found in this research pass; the closest authoritative fits are the general industrial IoT (IIoT) edge-connected guidance and the Azure IoT Edge offline-operations guidance cited above. This is a genuine gap — a training-simulator-specific reference architecture does not appear to exist publicly, so the design should be treated as a novel composition of the generic IIoT edge-connected pattern rather than an implementation of an existing named reference architecture.

### Recommended reference-architecture approach

Base the solution on Microsoft's **edge-connected IoT pattern** (Introduction to Azure IoT) combined with the **classic Azure IoT Edge offline-operations guidance**, using OPC Publisher (or an equivalent OPC UA/MQTT bridge module) as the southbound integration point and Azure Digital Twins/Fabric as the cloud-side consumer of synced telemetry — while explicitly documenting, as a design decision, the departure from Microsoft's newer default recommendation (Azure IoT Operations) due to its 72-hour offline ceiling, so that the choice and its rationale are auditable if Alliander or a future reviewer asks "why not the platform Microsoft currently recommends first."
